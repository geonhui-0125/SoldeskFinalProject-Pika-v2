# PIKA v2 관리자 기능 조사 및 재설계 제안

- 조사일 2026-11-11
- 상태는 기능 범위 검토안이다. P0·P1·후속은 제안 우선순위이며 사용자 승인 후 기능명세와 ERD에 반영한다.
- 거래 정책은 결제 샌드박스, 판매자 승인, 택배 수동 발송, 발송 전 구매자 취소, 발송 후·구매 확정 후 관리자 환불이라는 기존 결정을 따른다.
- 공개된 서비스 정책과 개발·운영 문서를 조사했다. 실제 서비스의 비공개 관리자 콘솔을 관찰한 자료는 포함하지 않았다.
- PortOne V2 문서를 결제 운영 기능의 조사 기준으로 사용했다. 실제 결제 연동 버전과 PG별 지원 범위는 API 계약 단계에서 확정한다.

## 1. 재설계 전 상태와 부족한 부분

### 화면과 코드에서 확인한 사실

조사 착수 시점의 Figma `08 V2 PC · 설계`에는 V1에서 복제한 회원·상품 관리와 관리자용 상품 목록·상세가 있었다. 표의 일부 값이 `undefined`로 표시되고 서비스 헤더·퀵메뉴가 운영 표 위에 겹쳤다. 이후 관리자 39개 화면 상태와 공통 셸·확인창을 설계했으며, 현재 디자인 기록은 [화면설계 기준](design-record.md#4-실제-진행한-설계와-확인-범위)에서 확인한다. 아래 코드 문제는 디자인 변경으로 해결된 것이 아니며 v2 구현 검증은 남아 있다.

| 확인 항목 | 근거 | 재설계에 필요한 조치 |
| --- | --- | --- |
| 회원 경고·제재가 실제 상태를 바꾸지 않음 | `AdminUserServiceImpl`의 상태 변경이 주석 처리됨 | 제재 명령·기간·해제·업무 접근 제한을 함께 설계 |
| 상품 위반·삭제·복구가 실제 상태를 바꾸지 않음 | `AdminProductServiceImpl`의 변경 코드가 주석 처리됨 | 판매 상태와 공개 상태를 분리한 숨김·복구와 처리 이력 |
| 회원 표와 DTO의 계약 불일치 | `users.js`는 `warningCount` 등을 표시하지만 `AdminUserDto`에서는 해당 필드가 주석 처리됨 | 관리자 전용 조회 DTO와 빈 값 표시 계약 |
| 상품 표와 DTO의 계약 불일치 | `products.js`의 `id`, `productName`과 DTO의 `productId`, `title`이 다름 | 프론트·서버 명세를 일치시키고 미정 값을 정상 상태로 해석하지 않음 |
| 전체 목록을 한 번에 조회 | 관리자 서비스가 `findAll` 결과를 목록으로 반환 | 서버 측 검색·필터·정렬·페이지 처리 |
| 제한적인 관리 흐름 | 목록 행의 경고·제한·위반·삭제 버튼 중심 | 상세 확인 → 영향 확인 → 사유 입력 → 실행 → 결과·이력 확인 |
| 직접 HTML 문자열로 데이터를 삽입 | 관리자 JS가 회원·상품 값을 `innerHTML`에 보간 | React의 텍스트 렌더링과 출력 처리로 사용자 작성 값 표시 |
| 관리자 권한 검사는 일부 존재 | `AdminController`의 `@PreAuthorize`, `@EnableMethodSecurity` | 새 API와 객체별 접근에도 검사를 적용. 기존 주석만 보고 권한이 없다고 판정하지 않음 |
| 관리자 환불 화면과 사건 처리 모델이 부족 | 기능명세의 `PAY-03`과 달리 관리자 화면에는 환불 업무가 없음 | 거래·결제·환불을 연결한 상세와 결과 미확정 처리 |

## 2. 외부 조사에서 얻은 설계 근거

### 신고와 제재는 처리 과정이 필요하다

당근의 공개 운영 사례는 금지 물품 안내, 경고와 게시글 미노출을 연결한다. PIKA에는 신고 사유 분류, 대상 게시글 확인, 처리 사유와 사용자 안내를 연결하는 최소 사건 처리 흐름을 제안한다. 다른 서비스의 제재 기간이나 금지 목록을 PIKA 정책으로 확정하지 않는다. [당근의 금지 물품 가이드라인 개편](https://about.daangn.com/company/pr/archive/%EB%8B%B9%EA%B7%BC-%EC%A4%91%EA%B3%A0%EA%B1%B0%EB%9E%98-%EA%B8%88%EC%A7%80-%EB%AC%BC%ED%92%88-%EA%B0%80%EC%9D%B4%EB%93%9C%EB%9D%BC%EC%9D%B8-%EA%B0%95%ED%99%94/).

### 결제 상태와 주문의 이행 상태를 구분한다

PortOne은 결제 내역에 상태·수단·모드 등의 필터를 제공하고, 취소는 API 또는 콘솔의 정식 경로로 수행하도록 설명한다. PIKA의 거래 상세에는 주문·배송·결제·환불 상태를 각각 표시하고, 샌드박스 표시와 환불 가능 잔액을 제시하는 것이 적합하다. [결제 내역 조회](https://developers.portone.io/opi/ko/console/guide/payments?v=v2), [취소·환불 연동](https://developers.portone.io/opi/ko/integration/cancel/v2/readme).

### 타임아웃은 실패 확정과 다르다

PortOne 문서상 브라우저 응답과 웹훅의 도착 순서는 보장되지 않으며, 웹훅 실패 시 재전송이 발생한다. 동일 요청을 안전하게 재확인할 수 있는 멱등 키도 제공한다. 이를 근거로 PIKA에는 결과 미확정 목록, 결제 재조회, 중복 방지, 재처리 이력을 제안한다. 내부 환불 요청 키의 유효성은 외부 제공자의 멱등 보장 기간과 별도로 유지한다. [웹훅 연동](https://developers.portone.io/opi/ko/integration/webhook/readme-v2), [PortOne REST API의 멱등 키](https://developers.portone.io/api/rest-v2).

### 권한과 감사 기록은 모든 관리 명령에 적용한다

OWASP는 최소 권한, 기본 거부, 요청별 권한 검사를 권고한다. 고권한 작업과 민감 정보 접근 기록도 다루며 로그에 남기지 말아야 할 정보도 구분한다. PIKA의 관리자 변경에는 대상·사유·처리자·시각·결과를 남기고, 개인정보 열람과 환불 실행 권한을 구체적으로 검사하는 안을 제안한다. [OWASP 권한 검사](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP 로깅](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

### 기술 운영 기능도 실행 결과를 추적한다

Elasticsearch는 작업 조회·취소 등 재색인 작업 관리 API를 제공한다. Gemini의 호출 제한은 요청 수·토큰 수 등으로 구분된다. PIKA에는 문서 단위 색인 복구와 AI 오류·사용량 조회부터 검토하고, 전체 재색인과 제한값 변경은 후속으로 둔다. 사용 중인 Elasticsearch 버전에 맞춰 실제 지원 API를 확정한다. [Elasticsearch 작업 관리](https://www.elastic.co/docs/reference/elasticsearch/rest-apis), [Gemini 호출 제한](https://ai.google.dev/gemini-api/docs/rate-limits).

이하의 기능·우선순위·화면 구성은 위 자료와 PIKA 명세를 바탕으로 한 설계 제안이다.

## 4. 핵심 업무 흐름

### 신고를 받아 상품을 숨기는 흐름

1. 신고 목록에서 미처리 사건을 연다.
2. 신고 사유, 신고 시점 상품 내용, 현재 상품·주문 상태를 확인한다.
3. 기각·상품 숨김·회원 조치 중 허용되는 작업을 선택한다. 신고만으로 자동 제재하지 않는 안을 제안한다.
4. 정책 사유와 내부 메모, 사용자에게 보낼 안내를 구분해 입력한다.
5. 서버가 최신 상태와 권한을 검사하고 처리한다.
6. 조치 이력과 검색 반영 상태를 확인한다. 처리 중 오류는 신고를 해결됨으로 표시하지 않는다.

최소 신고 상태는 `OPEN → IN_REVIEW → RESOLVED 또는 DISMISSED` 후보로 둔다. 경고·제한·숨김은 사건 처리 결과에 연결하는 별도 조치로 남긴다. 같은 사건을 동시에 처리하면 후속 담당자에게 최신 결과를 보여준다.

### 관리자 환불 흐름

1. 주문 상세에서 주문·배송·결제·환불 상태와 PG 조회 시점을 확인한다.
2. 환불 대상이 정상 채택 결제인지, 중복 성공 결제의 보상인지 확인한다.
3. 기존 환불과 진행·결과 미확정 요청을 고려해 환불 가능 잔액을 서버에서 계산한다.
4. 사유와 요청 키를 저장하고, 실행 직전 금액·대상·현재 상태를 재확인한다.
5. 외부 요청은 DB 잠금을 장시간 유지하지 않는 경로로 실행한다.
6. 성공·실패 확정·결과 미확정을 구분한다. 처리 중에는 중복 환불을 막는다.
7. 타임아웃은 재조회로 확인한다. 같은 논리적 환불의 재시도에서 새 요청을 무작정 만들지 않는다.
8. 발송 후 환불은 기존 구매 확정 이력과 상품의 재판매 판단 상태를 보존한다.

이 흐름은 기존 `REFUNDS`, `ORDER_TRANSITIONS`, `PRODUCT_CLAIMS` 설계에 맞춘다. 발송 이후 환불의 완료가 실물 회수나 재판매 허용을 뜻하지 않는다는 기존 정책을 화면에도 반영한다. [거래 정책](transaction-policy.md), [데이터 모델](data-model.md).

### 회원 제한 흐름

회원 상세 → 진행 거래 확인 → 제한할 행동·기간·사유 선택 → 영향 확인 → 실행 → 적용 결과·해제 이력 확인으로 구성한다.

신규 상품 등록·신규 구매·신규 대화 시작을 제한하더라도 이미 진행 중인 주문의 조회·취소·발송·환불 지원을 어떻게 제공할지는 별도 정책이 필요하다. 전면 접근 차단을 기본값으로 정해 거래 이행이 중단되는 상황을 피하는 안을 제안한다. 기존 토큰·WebSocket 권한 갱신도 같은 회원 상태를 기준으로 처리한다.

## 5. 화면 정보 구조와 보일러플레이트

관리자 메뉴 후보는 운영 홈, 회원, 상품·신고, 거래·환불, 처리 이력, 기술 운영으로 묶는다. 초기에는 한 관리자가 여러 업무를 처리할 수 있도록 하고, 담당자 배정·다단계 승인은 후속 검토한다.

| 화면 묶음 | 첫 화면 | 상세·보조 화면 |
| --- | --- | --- |
| 운영 홈 | 처리 대기 목록과 상태 요약 | 해당 사건·주문으로 이동 |
| 회원 | 검색·필터·페이지 목록 | 회원 상세, 진행 거래, 제한·해제 확인 |
| 상품·신고 | 상품 목록과 신고 접수함 | 상품 상세, 신고 검토, 숨김·복구 확인 |
| 거래·환불 | 주문 목록과 결제 이상 목록 | 주문 상세의 주문·결제·배송·환불·이력 탭, 환불 요청 확인 |
| 처리 이력 | 관리자 감사 목록 | 조치 상세와 원 사건·주문 링크 |
| 기술 운영 | 실패 작업 목록 | 웹훅·outbox·색인·AI 요청의 진단과 허용된 복구 |

`03 V2 PC · 디자인 보일러플레이트`에 관리자 셸, 필터 바, 데이터 표, 페이지 이동, 상태 배지, 상태 타임라인, 사유 입력, 영향 확인 모달, 처리 중·결과 미확정 패널을 추가하는 안이다. 원본 헤더·아이콘·공통 모달 스타일을 참조하고, 관리자용 사이드 메뉴는 전용 컴포넌트로 정의한다.

AI 버튼·찜 퀵메뉴 등 서비스 공통 요소의 관리자 화면 노출 여부는 관리자 셸의 명시적 표시 정책으로 검토한다. 화면별로 임의로 그리거나 숨겨서 서로 다른 구조가 되는 방식은 피한다. 모든 신규 화면은 원본 참조와 렌더링 검사를 거친다. [프로젝트 작업 지침](../AGENTS.md).

각 목록은 정상·빈 결과·조회 실패·권한 없음·조회 중 상태를 갖는다. 관리 명령은 입력 오류·처리 중·완료·명확한 실패·결과 미확정·다른 관리자와의 상태 충돌을 보여준다. 브라우저 새로고침 후에도 작업 ID로 결과를 확인할 수 있게 한다.

## 6. 데이터·기술명세에 미치는 영향

| 영역 | 유지·재사용 | 추가 검토 |
| --- | --- | --- |
| Oracle | 회원·상품·주문·결제·환불·전이·outbox의 주 저장소 | `REPORTS`, 신고 증거 참조, `MODERATION_ACTIONS`, 관리자 감사 이벤트 후보 |
| 회원 상태 | 계정 상태와 거래 역할 구분 | 제한 행동·기간·해제·기존 거래 이행 범위 |
| 상품 상태 | 판매 상태와 공개 상태 분리 | 사유·복구·검색 반영 상태 |
| MongoDB | 채팅·AI 대화 원본 | 신고 메시지 ID·증거 snapshot·보관 범위. Oracle과 Mongo 사이 FK를 가정하지 않음 |
| Redis | 메시지 처리 버퍼·짧은 실행 제어 | 업무 사건·제재·환불의 영구 이력은 Oracle에 저장 |
| Elasticsearch | 검색 및 운영 로그의 용도별 관리 | 상품 재색인과 공개 상태 동기화, 운영 로그 접근 범위 |
| Spring 모듈 | 업무 검증과 관리 API·권한 검사 | 각 도메인의 관리 명령을 공개 계약으로 호출. 관리자 모듈이 여러 저장소를 임의 직접 수정하지 않음 |
| Python gRPC·Gemini | AI 생성·검색 보조 | 사용량·요청 ID·실패 코드의 운영 조회 계약 |
| React MVVM | View·ViewModel·관리 API 책임 분리 | 필터 URL 상태, 서버 페이지 처리, 명령 결과·충돌 처리 |
| ELK | 기술 로그·추적·오류 분석 | 관리자 조치의 확정 이력과 업무 트랜잭션을 연결하는 식별자 |

감사 이벤트는 처리자, 대상, 조치 종류, 사유, 시각, 요청 키, 이전·이후의 허용된 상태, 결과, 추적 ID를 기록하는 후보로 둔다. 비밀번호·토큰·API 비밀키·전체 대화·전체 배송지를 통째로 감사 payload에 복제하지 않는다. 감사 저장 실패가 업무 변경과 분리돼 조치만 남는 상황을 막는다. ELK에는 필요한 식별자와 최소 진단 정보를 전달한다.

대량 색인과 이벤트 재처리는 작업 ID, 재시도 횟수, 처리 결과, 허용 대상을 기록한다. 검색 이벤트의 재처리를 결제·환불 명령 재실행과 혼동하지 않는다.

## 9. 포트폴리오 시연과 수락 기준

1. 신고 상품을 확인하고 사유를 입력해 숨긴다. Oracle과 검색 노출 결과가 일치하며 기존 주문은 유지된다.
2. 관리자 환불 요청을 중복 전송해도 외부 환불 효과와 내부 완료 이력이 중복되지 않는다.
3. PG 타임아웃 시 화면은 결과 미확정을 보여준다. 재조회 후 실제 결과를 반영하고 자동 재판매하지 않는다.
4. 두 관리자가 같은 사건을 동시에 처리하면 한 변경만 적용되고 다른 화면은 최신 상태로 갱신된다.
5. 제한 회원의 신규 행동은 차단하고 정책으로 허용한 기존 거래 이행은 가능하다. WebSocket에도 같은 상태를 반영한다.
6. 검색 반영이나 알림 소비가 실패하면 업무 결과를 보존하고 해당 소비자만 재처리한다.
7. 일반 회원이 관리 URL·API·다른 사건 ID로 접근하면 서버가 거부한다. 감사 기록에도 민감 원문을 남기지 않는다.
8. 관리자 표는 DTO 계약을 따르고, 누락 값·필터 결과 없음·API 실패·페이지 이동을 구분한다. 사용자 작성 문구를 HTML로 실행하지 않는다.

시드는 정상·위반 상품, 제한 회원, 진행 주문, 환불 실패·미확정, 중복 웹훅, 검색 반영 실패를 각각 재현한다. 운영 데이터 조회와 실행 API는 구현 단계에서 실제 권한·재처리 경계를 테스트한다.

먼저 주문 상세·관리자 환불의 정상·미확정·실패 화면, 신고 검토·상품 숨김, 회원 제한과 감사 이력을 설계하는 순서를 제안한다. 이 경로가 안정되면 대시보드와 기술 운영 화면을 확장한다.
