# CI/CD·시딩·부하 검증 계획

- 기록일: 2026-11-11
- 상태: 대화에서 논의한 실행 방향을 보존한 **구현 전 계획**. 현재 `.github/workflows`, v2 컨테이너 구성, 시딩·k6 스크립트는 없다.
- 기준: [기술명세](technical-spec.md), [기능명세](functional-spec.md), [거래 정책](transaction-policy.md).
- 구현 순서: 현행 화면·업무 계약을 구체화하고 새 프로젝트 구조에 맞춰 추가한다. 기존 V1 빌드 성공을 v2 테스트 성공으로 표시하지 않는다.

## 1. 배포 파이프라인 제안

GitHub Actions → GHCR → 단일 Linux 서버의 Docker Compose를 우선 후보로 둔다. PR에서 검사·테스트·빌드, main에서 이미지 생성, 지정 릴리스를 수동 배포하는 순서다. 배포 서버·도메인·비밀정보 관리·실제 런타임 버전은 미정이다. Kubernetes 도입은 기본 범위에 두지 않는다.

| 단위 | CI 검증 후보 | 배포 단위 |
| --- | --- | --- |
| React | 선정 도구의 타입·린트, ViewModel·화면 테스트, 프로덕션 빌드 | 정적 파일 제공 웹 이미지 |
| Spring | 컴파일, 업무 규칙·권한·상태 전이·모듈 경계 검사, 패키징 | 업무·메시징 단일 이미지 |
| Python AI | 린트·타입, 검색 파이프라인·gRPC 계약·취소 테스트 | 독립 AI 이미지 |
| 계약 | Protobuf 생성, HTTP·WebSocket 스키마와 소비자 호환성 | 관련 서비스 함께 검증 |
| 통합·E2E | Oracle·MongoDB·Redis 핵심 정합성, Playwright 사용자 흐름 | 테스트 환경 |

TypeScript·개별 검사 도구와 Spring Modulith는 아직 선정 전이다. 결정되지 않은 도구의 검사 성공을 필수 체크로 미리 표시하지 않는다. 코드·계약 변경은 연결된 검사를 수행하고 문서 변경에는 문서 검사를 적용한다.

이미지는 커밋 SHA로 식별하고 배포 릴리스에는 digest를 고정한다. 변경되지 않은 서비스는 이전 digest를 유지하며 서버에서 재빌드하지 않는다. DB·Redis·검색 저장소는 앱 배포 때마다 재생성하지 않고 버전·볼륨을 별도 관리한다.

수동 배포는 검증 릴리스 선택 → 이미지 pull → 필요 시 호환성을 확인한 DB 마이그레이션 → 앱 갱신 → 준비 상태와 HTTP/WebSocket/gRPC 연결 확인 → 실패 시 이전 이미지 구성 복구 순서다. DB 변경은 이미지 롤백과 별개이며 자동 역마이그레이션을 기본으로 하지 않는다. 배포 승인 기능의 사용 가능 여부와 패키지 공개 범위는 실제 저장소·계정 설정 단계에서 확인한다.

## 2. 재현 가능한 시딩

| 프로필 | 목적 | 주요 데이터 |
| --- | --- | --- |
| `functional` | 통합·Playwright | 역할과 주문 상태가 명확한 소규모 데이터 |
| `demo` | 포트폴리오 시연 | 이미지·설명·일관된 회원·거래·대화 |
| `load` | k6 | 매개변수로 조절하는 회원·상품·대화방·메시지 규모와 편향 |
| `search-eval` | 검색·RAG 평가 | 고정 상품·질문·관련도 정답 |

고정 난수 시드·기준 시각·시나리오 버전을 기록한다. 실행별 `runId`와 생성 ID manifest를 내보내 Playwright·k6가 같은 fixture를 사용한다. 데이터 추가와 전체 초기화를 분리하고, 정리 명령은 해당 실행이 소유한 개발·테스트 데이터에만 적용한다. 운영 저장소를 대상으로 실행하지 않는다.

상품 공개/판매 상태, 결제 미확정·승인 대기·배송·구매 확정·취소/환불, 리뷰 자격·중복 작성, 오프라인 수신·미읽음·다중 기기, 숨김·제한·신고·실패 작업을 시나리오로 생성한다. 도메인 제약을 건너뛰는 무작위 행 적재로 대신하지 않는다. 실제 PG·메일·Gemini 호출은 통제 가능한 대체 서비스로 바꾼다.

아래는 **목표 인터페이스이며 아직 실행할 수 있는 명령이 아니다**.

```text
./scripts/test-env up
./scripts/seed apply --profile functional --seed 42
./scripts/seed verify
./scripts/load run --scenario chat --dataset <manifest>
./scripts/seed cleanup --run-id <runId>
```

Oracle·MongoDB 데이터 정합성과 필요한 검색 반영 완료를 확인한 뒤 테스트를 시작한다. 검색용 임베딩은 모델·차원·상품 버전과 연결하고 무작위 벡터로 품질을 평가하지 않는다. V1 상품 예시는 정제 후 재사용할 수 있지만 기존 SQL을 v2 주문 모델의 시드로 그대로 실행하지 않는다.

## 3. 부하 도구와 측정

대화에서 선택한 부하 도구는 **k6**, 사용자 기능 검증은 **Playwright**다. HTTP·WebSocket·gRPC 경로를 각각 측정하고, 실제 채택한 k6 버전과 스트리밍 API를 구현 시 검증한다. k6를 쓰기 위해 별도 Grafana 서버를 반드시 추가하지는 않는다.

| 시나리오 | 확인 지표·정합성 |
| --- | --- |
| 상품 탐색 | 처리량, p95/p99, 오류율, 필터·정렬·페이지의 일관성 |
| 단일 상품 동시 구매 | 유효 주문/판매권 하나 유지, 예상 충돌 응답과 실제 오류 구분 |
| 채팅 | 연결 수, 저장 ACK·전달 지연, 중복·누락, 읽음·재접속 복구 |
| AI 스트리밍 | 첫 응답·전체 완료 시간, 취소 전파, 시간 초과·부분 응답 |
| 복구 | 소비자 중단·저장소 지연 이후 미처리 작업의 회복과 중복 효과 |
| 지속 부하 | 메모리·연결·버퍼·미처리 작업의 누적 여부 |

응답 코드만으로 정합성을 판단하지 않는다. 실행 후 manifest의 주문·메시지 ID와 저장 결과를 대조한다. 임계치는 작은 기준 측정 후 자원·요구에 맞춰 결정하며, 지금 임의의 RPS나 지연 목표를 확정하지 않는다.

PR은 작은 시드와 핵심 정합성 검사, 수동 성능 작업은 고정 자원·데이터·부하 조건을 사용한다. 실제 Gemini·PG 샌드박스는 별도 소규모 연동 작업으로 분리한다. 커밋 SHA, 시드 버전, 장비·컨테이너 제한, 부하 설정, 지표·로그와 실행 후 검증 결과를 남긴다.

현재 노트북은 RAM 약 14GiB이므로 무거운 통합 검사의 병렬 수를 제한하고 전체 ELK를 매 PR마다 실행하지 않는다. 서버와 부하 발생기를 같은 장비에서 실행한 결과는 개발 환경 상대 비교다. 시스템의 처리 한계를 주장하려면 발생기를 분리하고 발생기 자체 병목도 확인한다.

## 4. 구현 착수 체크리스트

- 새 프로젝트 구조·런타임·테스트 도구 결정 및 최소 CI 추가
- 도메인 마이그레이션과 `functional` 시드·검증기 작성
- 대체 PG/AI/메일과 거래·메시징 정합성 테스트
- Playwright 핵심 경로, k6 작은 기준 측정 후 부하·복구 확장
- 이미지 빌드·GHCR·릴리스 명세 구성
- 배포 대상·설정·백업·복구 절차 확정 후 수동 CD 연결

공식 참고 문서: [GitHub 이미지 게시](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images), [k6 프로토콜](https://grafana.com/docs/k6/latest/using-k6/protocols/), [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/). 링크는 기존 대화의 근거를 보존한 것으로 이번 문서화에서 새 버전 지원 여부를 재조사한 기록은 아니다.
