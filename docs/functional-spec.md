# PIKA v2 기능명세 초안

- 갱신일: 2026-11-08
- 상태: 원본 기능 대조와 v2 재설계의 1차 초안. 구현 완료를 의미하지 않는다.
- 거래 범위 확정: **결제 샌드박스·구매 확정·리뷰까지**.
- 검토 순서: 사용자 목적 → 기능·권한 → 상태·실패 처리 → 수락 기준 → 기술 선택.
- 관련 문서: [기술명세](technical-spec.md), [원본 대조 기록](functional-audit.md).

## 1. 사용자와 핵심 흐름

구매자와 판매자는 별도 고정 역할이 아니라 회원이 거래마다 갖는 역할이다. 관리자는 별도의 권한을 갖는다.

| 사용자 | 목적 | 핵심 흐름 |
| --- | --- | --- |
| 방문자 | 원하는 상품과 판매자 정보 탐색 | 목록·검색 → 상품 상세·공개 리뷰 → 로그인 |
| 판매자 | 상품 등록·문의 응대·거래 관리 | 상품 등록 → 가격 참고 → 채팅 → 주문 확인 → 거래 진행 |
| 구매자 | 상품 비교·구매·후기 작성 | 검색·AI 탐색 → 상세 → 채팅·찜 → 샌드박스 결제 → 구매 확정 → 리뷰 |
| 관리자 | 거래 환경 관리 | 회원·상품 조회 → 제한·숨김·복구 및 처리 사유 기록 |

AI는 상품 선택과 가격 비교를 보조한다. 결제·구매 확정·판매 상태 변경 같은 업무 명령의 최종 권한은 업무 서버가 검증한다.

## 2. 기능 목록과 완료 조건

`기본`은 첫 완성을 위한 제안 범위다. `후속`과 정책 미정 항목은 제거가 아닌 후속 검토 대상으로 관리한다. 사용자 확인 없이 제안 우선순위를 확정 범위로 취급하지 않는다.

| ID | 기능 | 범위 | 수락 기준 초안 |
| --- | --- | --- | --- |
| AUTH-01 | 가입·로그인·로그아웃 | 기본 | 중복 가입을 거부하고 인증 실패를 표시한다. 로그아웃·토큰 만료 뒤 보호된 요청을 거부한다. |
| AUTH-02 | 비밀번호 재설정 | 기본 | 만료·일회용 재설정 수단으로 변경하고 사용 완료된 수단은 재사용하지 못한다. |
| USER-01 | 내 정보·프로필 관리 | 기본 | 본인 정보만 수정하고 공개 프로필과 개인 연락·배송 정보를 구분한다. |
| USER-02 | 탈퇴·이용 제한 | 정책 검토 | 진행 거래·보관 이력·제한 계정의 로그인과 행동 범위를 정한 뒤 구현한다. |
| PROD-01 | 상품 등록·이미지 | 기본 | 제목·설명·가격·카테고리·상태를 검증한다. 실패한 업로드를 처리하고 등록 후 상세에 반영한다. |
| PROD-02 | 상품 수정·숨김·판매 상태 | 기본 | 판매자 본인만 변경한다. 거래 진행 중 가격·소유자 등 주요 조건을 변경할 수 없다. 거래 이력이 남는다. |
| SEARCH-01 | 키워드·카테고리·조건·페이지 조회 | 기본 | 조건을 결합하고 동일 정렬 기준에서 결과를 탐색한다. 판매 상태·가격 필터가 적용된다. |
| SEARCH-02 | 인기 검색어 | 후속 | 중복 집계·기간·개인정보가 포함된 검색어 처리 정책을 정의한다. |
| WISH-01 | 찜 등록·해제·목록 | 기본 | 중복 등록·반복 해제를 안전하게 처리하고 비공개·삭제 상품의 표시 규칙을 적용한다. |
| CHAT-01 | 상품별 1:1 대화방 | 기본 | 동일 상품·참여자 조합의 방 중복을 방지한다. 비참여자는 조회·송신·첨부 조회가 불가능하다. |
| CHAT-02 | 텍스트 송신·이력·재접속 | 기본 | 발신자는 인증 정보로 결정한다. 재전송이 중복 메시지를 만들지 않고 저장 확인·실패를 구분한다. |
| CHAT-03 | 읽음·여러 탭·기기 | 기본 | 접속 여부와 실제 읽음을 구분한다. 재접속 시 누락 이력과 읽음 위치를 복구한다. |
| CHAT-04 | 이미지 첨부 | 기본 | 파일 크기·종류·대화방 권한을 검증한다. 업로드 실패 시 메시지 전송을 성공으로 표시하지 않는다. |
| ORDER-01 | 주문 생성·구매 가능 여부 | 기본 | 서버가 상품·구매자·금액을 결정한다. 자기 상품 구매와 단일 상품의 동시 유효 주문을 제한한다. |
| PAY-01 | 샌드박스 결제·검증 | 확정 | 주문·구매자·PG 거래 ID·금액·상태를 확인한다. 반복 확인은 같은 결과를 반환한다. |
| PAY-02 | 결제 실패·중단·취소 | 기본 | 결과 미확정과 실패를 구분한다. 취소·환불 완료가 확인되기 전 재판매하지 않고 결제 이력을 보존한다. |
| TRADE-01 | 거래 진행·구매 확정·내역 | 확정 | 주문 당사자만 역할에 맞는 명령을 수행한다. 확정은 반복 호출해도 거래·알림을 중복 생성하지 않는다. |
| REVIEW-01 | 리뷰 작성·수정·삭제 | 확정 | 구매 확정한 본인 주문에 한해 1회 작성한다. 판매자·상품은 주문에서 도출한다. 수정·삭제 권한을 검증한다. |
| REVIEW-02 | 판매자 평점·공개 리뷰 | 기본 | 표시할 리뷰만 집계하고 리뷰가 없을 때 상태를 표현한다. 삭제·숨김 시 집계에 반영한다. |
| NOTI-01 | 거래·채팅 알림과 읽음 관리 | 기본 | 확정된 업무 이벤트에 따라 생성한다. 본인 알림만 접근하며 중복 이벤트로 알림을 중복 생성하지 않는다. |
| AI-01 | 상품 탐색 대화 | 기본 제안 | 조건에 맞는 근거 상품을 제시한다. 근거가 부족하면 부족함을 알리고 현재 구매 불가 상품을 구분한다. |
| AI-02 | 상품 시세 분석 | 기본 제안 | 실제 거래 통계와 등록가·외부 참고 정보를 구분하고 표본·기준 시점을 표시한다. |
| AI-03 | 판매자 리뷰 요약 | 후속 | 공개·유효 리뷰를 근거로 요약하며 표본 부족을 표시한다. |
| AI-04 | 생성 스트리밍·취소·이력 | 기본 | 시작·진행·완료·실패·취소를 구분한다. 타인 대화에 접근할 수 없고 재접속 시 최종 상태를 복구한다. |
| ADMIN-01 | 회원·상품 조회·제재 | 범위 검토 | 관리자만 수행한다. 제재가 실제 저장·접근 제한·공개 검색에 반영되고 처리 사유를 남긴다. |

## 3. 주요 권한 규칙

| 대상 | 읽기 | 변경 |
| --- | --- | --- |
| 공개 상품·판매자·리뷰 | 방문자 포함. 비공개·제재 상태 정책 적용 | 판매자 본인 또는 관리자의 명시적 관리 명령 |
| 개인 프로필·배송 정보 | 본인과 업무상 허용된 범위만 | 본인. 일반 공개 API에 포함하지 않음 |
| 대화방·첨부·메시지 | 대화방 참여자 | 참여자만 송신·읽음 변경. 발신자 ID를 요청값으로 신뢰하지 않음 |
| 주문·결제 | 거래 당사자. 응답 필드별 공개 범위 구분 | 구매자·판매자의 허용된 상태 전이 명령만 |
| 리뷰 작성 | 공개 리뷰 읽기 가능 | 해당 구매 확정 주문의 구매자. 수정은 작성자, 관리 삭제는 별도 권한 |
| AI 대화·생성 요청 | 해당 회원 | 해당 회원만 생성·취소·이력 관리 |
| 알림 | 수신자 본인 | 수신자 본인만 읽음·삭제 |

관리자가 모든 비공개 채팅·개인정보를 열람할 수 있다고 가정하지 않는다. 운영상 필요한 별도 권한과 감사 범위는 정책 결정 항목이다. 공개 상품 조회를 제외한 AI·채팅·거래 기능은 인증 회원을 대상으로 설계하는 제안이다.

## 4. 거래 상태 재설계안

현재 숫자형 상품 상태에 섞인 판매·주문·결제 흐름을 구분한다. 아래 이름과 전이는 후보이며, 판매자 승인·배송 처리의 필요성은 추가 결정한다.

| 객체 | 상태 후보 | 주요 전이와 주체 |
| --- | --- | --- |
| 상품 | 판매 중 / 거래 잠금 / 판매 완료 | 주문 확보 시 잠금 → 구매 확정 시 완료. 종료·실패 주문과 결제 결과 확인 후에만 판매 중 복귀 |
| 공개 상태 | 공개 / 판매자 숨김 / 관리자 숨김 / 삭제 표시 | 거래 상태와 별도 관리. 숨김·삭제가 기존 주문·메시지 이력을 제거하지 않음 |
| 주문 | 결제 대기 / 결제 완료 / 거래 진행 / 구매 확정 / 취소 처리 중 / 취소 완료 / 만료 | 결제 검증 후 완료, 허용된 당사자 명령으로 진행·확정. 만료는 결제 성공이 없음을 확인한 경우에만 적용 |
| 결제 시도 | 준비 / 결과 미확정 / 성공 / 실패 / 환불 처리 중 / 환불 완료 | PG 응답·조회·검증으로 갱신. 성공 이후의 취소는 환불 결과를 보존 |

### 지켜야 할 조건

- 한 상품은 동시에 한 유효 구매에만 배정한다. 결제 전 주문 금액과 상품 정보를 스냅샷으로 고정한다.
- 구매 확정은 결제 성공·거래 진행 조건을 만족한 주문의 구매자만 수행한다.
- 리뷰 자격은 결제 레코드 존재가 아닌 구매 확정 주문을 기준으로 한다. 주문당 리뷰 중복을 DB에서도 방지한다.
- PG와 Oracle은 하나의 로컬 트랜잭션으로 묶이지 않는다. 결제 성공 후 로컬 저장 실패, 늦게 도착한 성공 응답, 중복 통지를 재조회·재처리로 복구한다.
- DB 잠금을 외부 API 응답을 기다리는 동안 장시간 유지하지 않는다. 잠금·조건부 변경 방식은 동시 구매 테스트에 근거해 결정한다.
- 취소는 결제 이력 삭제가 아니다. 복구·재판매 시점은 PG의 확인된 결과에 따른다.
- 거래 확정 뒤 알림·검색 갱신은 재처리 가능한 이벤트로 처리한다. 부가 기능 실패가 완료된 결제를 실패처럼 표시하지 않도록 한다.

### 먼저 정할 거래 정책

판매자 승인 필요 여부, 배송·직거래 구분, 구매 확정 가능 시점, 결제 대기 만료 시간, 취소 가능 주체·시점, 구매 확정 후 환불·분쟁 범위가 미정이다. 실제 정산·실결제 운영 범위는 샌드박스 범위와 별도로 결정한다.

## 5. 사용자 채팅·AI의 상태와 실패 처리

| 상황 | 기대 동작 |
| --- | --- |
| 중복 송신·재시도 | 같은 메시지 ID는 같은 처리 결과를 반환한다. 다른 본문을 같은 ID로 보내면 거부한다. |
| 서버가 수신했으나 저장 전 장애 | 수신 접수와 영구 저장 완료를 구분한다. Redis 보존 정책 내 재처리와 클라이언트 재전송 기준을 정한다. |
| MongoDB 저장 후 실시간 전달 실패 | 저장된 메시지를 재접속 시 조회한다. 저장된 메시지를 다시 생성하지 않는다. |
| 상대가 온라인이지만 대화방을 보지 않음 | 읽음으로 처리하지 않는다. 읽음 위치는 별도 확인 이벤트로 갱신한다. |
| 느린 연결·버퍼 초과 | 버퍼를 무한 증식시키지 않는다. 오류·종료 정책과 이력 복구 경로를 제공한다. |
| 회원 제한·토큰 만료·대화 접근 철회 | 새 요청을 제한하고 기존 연결·구독의 유효성을 처리한다. |
| AI 요청 제한·외부 API 오류 | 재시도 가능 여부를 표시하고 무제한 재시도하지 않는다. 사용자 메시지와 실패 상태를 보존한다. |
| AI 생성 중 취소·연결 종료 | 명시적 취소와 일시 단절을 구분한다. 부분 응답 보존 여부·유예 시간·취소 후 도착한 조각 처리는 정책 확정 필요 |
| AI 답변 근거 없음·부족 | 상품·가격을 만들어내지 않고 부족한 조건·표본을 설명한다. |

## 6. 기능에서 기술로 연결하는 검토표

| 요구 기능 | 필요한 기술적 책임 | 기술 선택을 검증할 기준 |
| --- | --- | --- |
| 구매·확정·중복 방지 | Oracle 주문·결제 모델, 트랜잭션, 제약·동시성 제어 | 동시 구매·중복 응답·결제 후 저장 실패 복구 |
| 본인·참여자 권한 | Spring 인증·업무 모듈과 메시징 모듈 계약 | HTTP와 WebSocket에서 같은 접근 규칙 적용 |
| 채팅·AI 대화 이력 | MongoDB와 대화 저장 소유 모듈 | 커서 조회·접근 권한·중복 방지·재접속 |
| 메시지 버퍼·재처리 | Redis 처리 경로 | ACK 시점·미처리 복구·보존 한도. 서버 간 중계는 다중 인스턴스 요구가 생길 때 검토 |
| WebSocket 연결·AI 전달 | Spring 내부 메시징 모듈 | 버퍼·실행 수 제한·취소·연결 생명주기. 별도 언어·서비스는 기본 전제로 두지 않음 |
| 상품 탐색·AI 추천 | 검색 인덱스·임베딩·필터·리랭킹 | 키워드 대비 검색 품질과 지연 개선. RAG 단계별 효과 비교 |
| 가격·재고의 최신성 | Oracle 원본 확인·검색 동기화 | 색인 지연에도 구매 불가 상품을 구분하고 잘못된 가격으로 주문하지 않음 |
| AI 검색·도구 실행·평가 | Python gRPC·Gemini와 업무 API 경계 | 모델 교체 자체보다 권한·근거·취소·지연·품질을 검증 |
| 운영·문제 원인 추적 | ELK·요청 추적·지표 | 주문·메시지·AI 요청 ID로 처리 흐름과 실패 원인 확인 |

## 7. 기능 재설계 진행 순서

1. 사용자 흐름과 기능별 첫 완성·후속 범위를 검토한다.
2. 주문·결제·상품 상태와 권한·취소 정책을 확정한다.
3. 채팅·AI의 이벤트·이력·재접속·취소 정책을 확정한다.
4. 화면별 정상·빈 결과·오류·로딩 상태와 MVVM 책임을 정한다.
5. 모듈 공개 API·HTTP·WebSocket·gRPC 계약과 저장 모델을 정한다.
6. 검색 품질·메시징 부하·운영 자원 실험으로 기술 후보를 검증한다.
7. 기능별 수락 기준을 테스트에 연결하고 작은 사용자 흐름 단위로 구현한다.
